# Untexted Backend

Minimal FastAPI backend for Untexted. Python 3.13 is required.

## Local setup

From the repository root:

```sh
cd backend
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

The virtual environment is local to `backend/` and is ignored by Git.

## Database configuration

The backend reads the PostgreSQL connection string from `DATABASE_URL`. For a
local process connecting to PostgreSQL on the host:

```sh
export DATABASE_URL="postgresql://<user>:<password>@localhost:5432/<database>"
```

The application converts `postgresql://` and `postgres://` URLs to the
`postgresql+asyncpg://` driver URL internally. The URL provided by
`compose.yaml` can therefore be used without changes.

If `DATABASE_URL` is not set, the application still starts and `/health`
continues to work, but `/ready` returns HTTP 503.

## User model

The first domain model is `User` in `app/models/user.py`, exported from
`app/models/__init__.py`. It maps to the `users` table:

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key, generated by PostgreSQL with `gen_random_uuid()` |
| `username` | `varchar(32)` | Required, unique (`uq_users_username`) |
| `display_name` | `varchar(100)` | Required |
| `password_hash` | `varchar(255)` | Required; Argon2id hash, never returned by the API |
| `created_at` | `timestamptz` | Required, default `now()` |
| `updated_at` | `timestamptz` | Required, default `now()`; refreshed on SQLAlchemy updates with `onupdate=func.now()` |

The model is registered with `Base.metadata` from `app/database.py`. Alembic
imports `app.models` so migrations and `alembic check` see the model.
Registration is implemented; login, sessions, email verification, and profile
endpoints are not.

## Registration API

`POST /auth/register` creates a user and returns HTTP 201 with public profile
data. The password is hashed with Argon2id before it is written to PostgreSQL;
only the encoded hash is stored in `users.password_hash`.

Request fields:

| Field | Rules |
|---|---|
| `username` | Required, 1-32 characters: lowercase Latin letters (`a-z`), Cyrillic letters (`а-я`, `ё`), digits (`0-9`), underscores (`_`), and hyphens (`-`) only |
| `display_name` | Required, 1-100 characters: Latin and Cyrillic letters, digits, spaces, and printable ASCII special characters, including ASCII emoticons; emoji are rejected |
| `password` | Required, 8-128 characters; must not be empty or contain only whitespace, and is never trimmed |

Unknown fields, including `id`, `created_at`, and `updated_at`, are rejected
with HTTP 422 by the Pydantic request schema.

Example request:

```sh
curl -X POST http://127.0.0.1:8000/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","display_name":"Alice","password":"<your-password>"}'
```

Example response:

```json
{
  "id": "5f0c1c1e-7d1a-4e4a-9c7e-3f0b1a2c3d4e",
  "username": "alice",
  "display_name": "Alice",
  "created_at": "2026-10-26T18:29:07.271400Z"
}
```

The response never contains the password or `password_hash`.

Error responses:

- HTTP 422: FastAPI validation errors. Password values are redacted from the
  error details.
- HTTP 409: `{"detail":"Username already taken"}` when PostgreSQL rejects a
  duplicate username through `uq_users_username`.
- HTTP 503: the database is not configured when the application starts.
- HTTP 500: `{"detail":"Could not create user"}` when the user cannot be
  saved, including database connection or write errors. Internal SQL and
  connection details are not returned.

The endpoint relies on the PostgreSQL unique constraint as the source of truth;
it does not use a pre-check to guarantee uniqueness.

## Authentication configuration

The session cookie and CSRF checks are configured through environment
variables:

- `COOKIE_SECURE=true` enables the `Secure` cookie attribute. Use this in
  production behind HTTPS.
- `ALLOWED_ORIGINS` is a comma-separated list of permitted origins for CSRF
  checks. If unset, the request's own origin is allowed.
- `CSRF_STRICT=true` or `ENVIRONMENT=production` rejects unsafe requests
  without a valid `Origin` or `Referer`.
- `TRUSTED_PROXIES` is a comma-separated list of proxy addresses allowed to
  provide `X-Forwarded-For`.
- `LOGIN_RATE_LIMIT_ACCOUNT`, `LOGIN_RATE_LIMIT_ACCOUNT_WINDOW_MINUTES`,
  `LOGIN_RATE_LIMIT_IP`, and `LOGIN_RATE_LIMIT_IP_WINDOW_MINUTES` configure
  the in-memory login rate limiter.

Passwords are hashed with Argon2id through `argon2-cffi`, using the RFC 9106
low-memory profile and a fresh random salt for every password. See
[decisions/0002-password-hashing.md](../docs/decisions/0002-password-hashing.md).

## Authentication API

`POST /auth/login` authenticates a user with username and password and creates
a server-side session. On success it returns HTTP 200 with `UserPublic` and
sets an HttpOnly session cookie.

`POST /auth/logout` revokes only the current session, clears the cookie, and
returns HTTP 204. It is idempotent when no cookie is present.

`GET /users/me` returns HTTP 200 with the authenticated user's `UserPublic`.
Without a valid session it returns HTTP 401.

Session cookies use:

- name: `session`;
- `HttpOnly=true`;
- `SameSite=Lax`;
- `Path=/`;
- `Max-Age=1209600` (14 days);
- `Secure` only when `COOKIE_SECURE=true`.

The raw session token is never stored in PostgreSQL. Only its SHA-256 hash is
stored in `sessions.token_hash`.

Sliding expiration extends a session by 14 days when less than 24 hours
remain. The cookie `Max-Age` is updated in the same response.

Login attempts are rate-limited in memory:

- 5 failed attempts per `(username, IP)` in 15 minutes;
- 50 failed attempts per IP in 15 minutes.

When a limit is exceeded, the API returns HTTP 429 with `Retry-After`.
The limiter is process-local and is reset on restart. It does not permanently
lock accounts. Behind a reverse proxy, set `TRUSTED_PROXIES` to the proxy
address before trusting `X-Forwarded-For`.

Basic CSRF protection checks `Origin` or `Referer` for unsafe methods. In
production set `ALLOWED_ORIGINS` and `CSRF_STRICT=true`. `SameSite=Lax` is
not considered sufficient CSRF protection by itself.

Error responses do not reveal whether a username exists and do not include
passwords, password hashes, session tokens, or SQL details.

## Database migrations

Alembic manages database schema migrations. The configuration is in
`alembic.ini`, and migration scripts are stored in `alembic/versions/`.

The database URL is not stored in `alembic.ini`. `alembic/env.py` reads
`DATABASE_URL` and converts it to the `postgresql+asyncpg://` driver URL used by
the application. Commands that connect to the database exit with an error if
`DATABASE_URL` is not set.

### Run migrations locally

PostgreSQL must be reachable from the host. The `db` service in `compose.yaml`
does not publish a port, so use the Docker Compose command below unless you run
PostgreSQL separately or provide temporary port forwarding.

With the virtual environment activated and `DATABASE_URL` set:

```sh
cd backend
alembic current
alembic upgrade head
alembic downgrade -1
```

### Run migrations through Docker Compose

The backend image installs Alembic from `requirements.txt`, but the current
Dockerfile does not copy the Alembic configuration into the image. Mount the
backend directory when running a migration container:

```sh
docker compose build backend
docker compose run --rm -v "$PWD/backend:/app" backend alembic upgrade head
docker compose run --rm -v "$PWD/backend:/app" backend alembic current
```

The `backend` service supplies `DATABASE_URL` with the `db` hostname, so the
command connects to the PostgreSQL container without exposing its port.

### Create a migration

With a reachable database and `DATABASE_URL` set:

```sh
cd backend
alembic revision --autogenerate -m "describe the change"
```

`target_metadata` is `Base.metadata` from `app/database.py`. Future models
should inherit from `Base` and be imported by the migration environment so they
register in that metadata before autogenerate runs.

The current migration head is revision `20261026_0004`
(`20261026_0004_create_sessions_table.py`). Revision `20261026_0002`
creates the `users` table, revision `20261026_0003` adds the required
`password_hash` column, and revision `20261026_0004` creates the
`sessions` table.

The password hash migration adds a `NOT NULL` column without a data backfill.
It is safe for the current schema because registration did not exist before
revision `20261026_0003` and the table has no users. A database that already
contains users would need an explicit data migration strategy instead.

The initial migration creates `schema_migrations_check`, a temporary technical
table used to verify upgrade and downgrade. It is not part of the application
data model, is preserved by the users migrations, and is excluded from
autogenerate.

## Run locally

With the virtual environment activated:

```sh
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

The liveness endpoint does not depend on PostgreSQL:

```sh
curl http://127.0.0.1:8000/health
```

Expected response:

```json
{"status":"ok"}
```

The readiness endpoint checks the database with `SELECT 1`:

```sh
curl -i http://127.0.0.1:8000/ready
```

It returns HTTP 200 with `{"status":"ok"}` when PostgreSQL is available and
HTTP 503 with `{"status":"unavailable"}` otherwise.

## Run tests

With the virtual environment activated:

```sh
python -m pytest
```

Unit tests import the FastAPI application directly and do not require a running
server or PostgreSQL. The database session is replaced with a dependency
override in the readiness and validation tests.

The model and validation tests also run without PostgreSQL. Database
integration tests are skipped unless `TEST_DATABASE_URL` is set to a disposable
database with the migrations applied:

```sh
cd backend
export TEST_DATABASE_URL="postgresql://<user>:<password>@localhost:5432/<database>"
DATABASE_URL="$TEST_DATABASE_URL" alembic upgrade head
python -m pytest tests/test_auth_database.py tests/test_registration_database.py tests/test_user_database.py
```

The integration tests verify the real table, constraints, registration,
password hashing, username conflict handling, rollback behavior, and
`updated_at` behavior. They create users with unique usernames and remove only
the users they created. The tests also refuse to run if `TEST_DATABASE_URL`
points to the same database as `DATABASE_URL`.
